Fleet keeps the setup of your coding agents the same everywhere. Instructions, skills, MCP servers, settings and encrypted secrets live in one private git repo, and every machine is made to match it.

How it works

Write it once. Every machine follows.

Your config is a git repo you own. fleet push publishes it and applies it on every host it can reach over ssh. Every machine also pulls and applies on its own every 30 minutes.

fleet push

Watch it land.

On a terminal, fleet push shows each step as it happens: validate, publish, then one line per host with its stage, a bar for the step it is on, and its time. When it ends, the block turns into a summary that stays in your scrollback. Everything below was recorded from the real command.

fleet push 

      

      
Hosts run one at a time. The conflict on server stops it and tells you the fix; fleet never overwrites what it did not write.


      

        
Piped, or in CI

        
Without a terminal there is no block to redraw. You get one timestamped line when each host starts and when it has a result, plus anything a host says. NO_COLOR turns the color off and keeps the block; piping is how you get plain lines. The result on stdout and in --json is the same either way.

What it keeps in line

        
Everything your agents need. Nothing they shouldn't.

        
How it works shows what fleet manages. These parts keep it safe to run on every machine and get a machine's setup into your config.

      

      

        

          

            
!

            
Conflicts, never overwrites

            
If a machine holds something different from your config, fleet stops and tells you exactly what and how to fix it. Hand edits and tool-written changes are never silently replaced.

          

          
✕ ~/.claude/CLAUDE.md is a file, not a link
  fix move it aside, then run fleet apply

        

        

          

            
✓

            
Skill review

            
A skill is instructions your agent follows, so an update from someone else changes what it does. fleet skills update --review reads what a source would bring in before its pin moves: the commits, the skills you use that changed, and a flag for each new script, new URL or wider allowed-tools.

          

          

        

        

          

            
▤

            
Startup context

            
Before your first prompt, each agent has already loaded your instructions, the descriptions of your skills and the tool definitions of your MCP servers. fleet context draws that as bars, in estimated tokens, with every host on one scale, so you see which machine and which server weighs the most. It only reads files and starts no server.

          

          

        

        

          

            
⇣

            
Capture

            
Set something up on one machine first, with claude mcp add or a skill folder. Then fleet capture turns the servers and skills that machine has and your config does not into config. It asks about each one, writes the catalog and the host files, and commits. A token in a server's env or headers moves into sops on the way, and no value is ever printed. It reads only the machine it runs on. Capture has the details.

          

          
$ fleet capture
[h]ost / [a]ll hosts / [i]gnore / [s]kip / [q]uit: h
ISSUES_API_KEY becomes the secret ISSUES_API_KEY.
Press enter, or type another name:
Push now? [y/N]

Compare

        
Why not just dotfiles?

        
You could keep agent config in chezmoi or a Nix flake. A dotfiles manager usually owns whole files, though, and agents write to their own config files all the time. This is what fleet does differently.

      

      

        

          
✕ A dotfiles manager

          
✓ fleet

        

        

          
Owns all of settings.json
Claude Code writes to that file itself, so when the manager owns the whole file, the next apply overwrites what the agent wrote.

          
Owns only the keys you list
Fleet sets the keys your config lists, like attribution, and leaves the rest of the file to the agent. Hand edits to its keys are a conflict, not a silent overwrite.
~/.claude/settings.json
  attribution.commit   fleet's
  permissions.allow    the agent's
  model                yours

        

        

          
An MCP server per agent, per file
Each agent stores MCP servers in its own file and shape, so you keep a copy per agent in sync by hand.

          
One catalog entry, every agent
Define the server once in catalog/mcp.yaml. Fleet writes it in each agent's own format, and fleet doctor starts it to check it answers.

        

        

          
Waits for you on each machine
You run an update or a rebuild on every host and hope you didn't forget one.

          
Reaches them for you
fleet push applies on every host over ssh while you watch. Machines it can't reach catch up on their own 30-minute timer.

        

        

          
Skills are just files
An upstream skill changes what your agent does, and nothing shows you the change before it lands.

          
Skills are pinned and reviewed
Every source is pinned to a commit. --review shows what an update brings in, with new scripts and URLs flagged.

        

      

      

        
Keep chezmoi for your dotfiles.Fleet only owns agent config, so the two sit side by side as long as chezmoi does not manage ~/.claude.

        
All in on Nix?home-manager has Claude Code and opencode modules. Fleet works without Nix, keeps encrypted secrets per host and stops at conflicts.

        
Rules for many agents?rulesync generates config for more than 60 AI coding tools from one set of rule files. Fleet keeps the setup of your coding agents the same on every machine.

23 Nov 2026
15 added3 changed1 you need to do

  
Added
  • fleet capture turns the MCP servers and skills a machine has, and your config does not, into config. On a terminal it asks about each item: add it for this host, add it for every host, ignore it, or take over one that already matches. Then it writes the catalog, the picks and the secrets files, commits, and asks before it pushes. A server that two agents have in different forms is one item, and you pick one definition. A value whose name looks like a secret (*_TOKEN, *_KEY, *SECRET*, *PASSWORD*, Authorization) becomes secret:NAME and is encrypted with sops. For any other value it asks, secret or plain. No value reaches the catalog, an output, --json or the page. A skill in a git repo with a remote makes that repo a pinned source with review: true and a bundle. After a capture this machine is taken over as it stands, so the next apply has nothing to change. fleet capture mcp|skill <name> --host|--all|--ignore answers for one item, --yes takes the defaults, and --no-push stops after the commit. Without a terminal, or with --json, it only reports. It reads only the machine it runs on. fleet ui has a Capture screen after Hosts with the same choices, and each choice goes on To push. See Capture.
  • unmanaged: in a host file lists mcp:<name> and skill:<name> items that capture does not list or count again. fleet status shows not from config: N, status --json has unmanaged, and each host card of the bridge and the page says how many are not from config. Older readers of status --json ignore the field.
  • fleet undo [--no-push] [--yes] [<commit>] reverts the last recorded push, or a named one, and pushes the revert to the same scope. --no-push stops after the revert commit, and --yes skips the prompt. If the revert clashes with a newer commit, undo refuses with exit 3, commits nothing and names the clashing files and the newer commit. When the push changed a secrets file, the message says the revert brings back the old encrypted values. The push history screen of the bridge has a u key that runs the same undo on the selected entry after the same confirmation.
  • The apply timer's schedule is configurable. timer: in hosts/_defaults.yaml sets it for every machine, and in a host file for that one, the host file winning. Without it the timer runs every 30 minutes, as before. Valid values are 5m, 10m, 15m, 20m, 30m, a whole hour 1h to 24h, and off, the schedules both systemd and launchd can express. Anything else is a config error that names them. On a Mac a whole number of hours becomes the calendar entries that divide the day, so a run missed while the Mac slept still happens when it wakes. timer: off makes apply stop the timer and delete the systemd unit and timer, or unload and delete the LaunchAgent, so nothing is left running. Setting a value again installs it back. Apply now keeps the installed timer in step, not only fleet init: the next apply rewrites and restarts it when it differs, fleet diff lists the change like any other, and a scheduler that apply cannot reach is a warning, not a failed apply. fleet status shows the schedule beside the timer's state, in text and as schedule in --json, and fleet doctor no longer fails the timer check on a machine whose config says off. On a Mac, a schedule change applied by the LaunchAgent's own run is loaded after that run has exited, so the agent is never booted out from under the apply that is changing it. A host set up before timer: existed has nothing to change on its first apply. See the timer's schedule.
  • A machine now sends an alert when an apply on its timer stops. notify: in hosts/_defaults.yaml or a host file sets where a machine sends alerts. A host file overrides the defaults one field at a time, and notify: off turns every alert off for that machine. With no notify:, nothing changes. The channels are desktop: true (notify-send on Linux, osascript on a Mac, skipped without an error where there is no desktop session), ntfy: (the full topic URL, with an optional ntfy_token:) and webhook: (a POST of a small versioned JSON body: v, host, event, message, conflict, time, fleet). A problem goes to ntfy at high priority with a warning tag, and back to ok at default priority. ntfy, ntfy_token and webhook may be secret:NAME, and a secret is what to use for each. Each machine alerts about itself, only after a run its own timer started, never after fleet push, a manual fleet apply or fleet init. The events are a new conflict, an apply that stops with a real error, and back to ok after either. Warnings, another apply already running and a config repo that cannot be reached are not alerts. A machine remembers its last state in ~/.local/state/fleet/notify.json, so nothing repeats, and the first run after alerts are turned on alerts once if the machine is already in a conflict or failing. A message holds the machine's name, what happened, the first conflict's kind and path and the command to run, never a secret or a file's content. A failed delivery never fails the apply: it is a line in the apply log, and the next change of state tries again. fleet notify --test sends a test alert through every channel the machine has and reports each. fleet status has an alerts: line, for example alerts: desktop, ntfy · last sent 2h ago (conflict), followed by · ntfy failed: HTTP 403 when a delivery failed. status --json has alerts, and the bridge's host card shows a mark when the last delivery failed. See alerts.
  • fleet host remove <name> retires a machine from the command line, with the same code as the Remove button of fleet ui. It deletes the host file and its secrets file, rekeys, commits and pushes. It refuses the machine you run it on and the last admin host, and it asks first (without a terminal it needs --yes). If the machine has an ssh destination and answers, it asks once whether to stop and remove its timer there. The agent config, skills and links stay. It ends with the secrets the machine could read and offers to rotate them. See Retiring a machine.
  • fleet secrets rotate [NAME...] replaces secret values one by one with hidden input. It sets each new value in every secrets file that holds the secret, makes one commit, then offers to push and to run fleet doctor --all. It reminds you to revoke the old tokens, which fleet cannot do. A value is never echoed, logged or put in --json. The Remove host dialog of fleet ui ends with a Rotate these now button that opens the Secrets screen on those names.
  • fleet context --usage shows how often each MCP server and skill was used in the last 30 days: its calls and the share of sessions it was called in, next to its size. It also says how much history each agent had. A server or skill never called in 30 days that costs real tokens gets one line, "consider exclude". Fleet only reports and changes nothing. Claude Code (transcripts) and opencode (its SQLite database, read with node:sqlite) are read, and Antigravity CLI says "no readable history". An agent that cannot be read says why, and the others are still shown. A skill you ran or typed as /name counts, a typed command only by its name, and a subagent counts toward its session. --all has every host count its own history and send names and numbers, which are added up here, and --json adds usage. The bridge's Context tab has a u key for it. Only tool names, skill names, session ids and times are read. No prompt, file or tool output is kept, printed or sent, and the output ends with "read locally, names and counts only". See usage.
  • fleet card writes fleet-card.svg (1200 x 630), an image of your fleet to share in a post, a GitHub discussion or a README. It shows the counts of machines, agents, skills and MCP servers, each machine with its agents and OS, and a year of changes as a GitHub-style activity grid when the config repo had at least 20 commits in the last 12 months. --style map puts the config in the middle with each machine around it, --badge writes a small fleet-badge.svg for a README, and --names shows the real hostnames. Without --names they are host 1, host 2. No server, skill, skill source or secret name is ever on the card. It prints what is on the card before it writes the file, reads what fleet last saw of each host and asks none. fleet ui has a Card screen with the same two styles and a names switch, Save PNG, Copy image, and Post to Show and tell, which opens a new discussion in the project with a short text filled in. fleet status --json now has os (linux or macos), which the card shows for each host.
  • fleet ui opens on a new Fleet screen. It has a card for every host: ok, or its first conflict with a button that shows the fix, or unreachable with when it was last seen, or a timer host. It also shows when each host last applied, its timer and agents, and the startup context of every host and agent as bars on one scale, as fleet context --all draws them. It shows what was last seen at once, marked not live, then asks every host when the screen opens and on Refresh, never on a timer. It shares the bridge's memory file, so the page and the bridge open on what the other saw.
  • fleet doctor now reports bad-auth when a server answers HTTP 401 or 403 with configured credentials. It names the secret:NAME values the server uses, which secrets file holds each one, and when that value was last set in the file's git history. The text and --json output include this, and the bridge marks it as a failure. A server that wants a login and has no configured credentials is still auth-needed (neutral). Replace the value with fleet secrets rotate or in the Secrets screen of fleet ui.
  • The docs are pages on the site at rolflab.nl/fleet/docs/, with a side navigation, a search field on every page and a docs home that links to every page. npm run site:docs builds them from docs/*.md (the releasing guide stays for maintainers), and a test fails when a doc changes without it. docs/getting-started.md is new and holds the README's Getting started and Working with fleet sections, so the README is shorter. The landing page and the changelog page link to the docs now.
  • The command reference is a page of the docs, at rolflab.nl/fleet/docs/commands/. It lists every fleet command and option, whether it only reads or changes something, its --json fields and a link to the guide that covers it. It is written from the command list that fleet help prints, so it cannot drift from the tool, and npm run docs:commands rebuilds docs/commands.md.
  • The docs have a Reference section with one page per config file: fleet.yaml, the host files and hosts/_defaults.yaml (and how a host file layers on the defaults), catalog/mcp.yaml and catalog/skills.yaml. Each key has its type, default, what it does, an example and the version that added it. The list of keys each loader accepts is now kept in one place in the tool, and a test fails when a key has no entry in the reference or an entry names a key the loader does not know.
  • The landing page has a card for Capture and a section for fleet card, with a card in each style and the README badge. Its fleet ui screenshots show the Fleet screen and the Matrix.

  
Changed
  • Removing the last key under a map from a host file now takes the map too. Before, fleet deleted only the key, so a provider or section you took out of settings left empty maps behind in the tool's file ("provider": {"x": {"models": {"m": {}}}}), and a tool that lists those names, such as opencode's model picker, kept showing them. Fleet now deletes each map above a removed key that the removal leaves empty, nearest first, and stops at the first one that still holds anything. The top level stays, and an empty map elsewhere in the file is not touched. A map that is emptied and refilled in the same apply keeps its place in the file.
  • fleet help lists every option of every command, not only those of bridge, push and ui, from the same list the command reference is written from.
  • The hint under a bad-auth server in fleet doctor, the bridge and the page now points to fleet secrets rotate.

  
You need to do
  • Every host has to run this version before a host file uses unmanaged:, timer: or notify:, because an older fleet rejects a key it does not know. Move your pin with fleet update, read what it prints, and fleet push, before you add one of them. After you add notify:, set the secrets it names with fleet secrets set <host> NAME and try it with fleet notify --test on each machine.
