Fleet keeps the setup of your coding agents the same everywhere. Instructions, skills, MCP servers, settings and encrypted secrets live in one private git repo, and every machine is made to match it.

How it works

Write it once. Every machine follows.

Your config is a git repo you own. fleet push publishes it and applies it on every host it can reach over ssh. Every machine also pulls and applies on its own every 30 minutes.

What it keeps in line

        
Everything your agents need. Nothing they shouldn't.

        
How it works shows what fleet manages. These are the parts that keep it safe to run on every machine.

      

      

        

          

            
!

            
Conflicts, never overwrites

            
If a machine holds something different from your config, fleet stops and tells you exactly what and how to fix it. Hand edits and tool-written changes are never silently replaced.

          

          
✕ ~/.claude/CLAUDE.md is a file, not a link
  fix move it aside, then run fleet apply

        

        

          

            
✓

            
Skill review

            
A skill is instructions your agent follows, so an update from someone else changes what it does. fleet skills update --review reads what a source would bring in before its pin moves: the commits, the skills you use that changed, and a flag for each new script, new URL or wider allowed-tools.

          

          

        

        

          

            
▤

            
Startup context

            
Before your first prompt, each agent has already loaded your instructions, the descriptions of your skills and the tool definitions of your MCP servers. fleet context draws that as bars, in estimated tokens, with every host on one scale, so you see which machine and which server weighs the most. It only reads files and starts no server.

Compare

        
Why not just dotfiles?

        
You could keep agent config in chezmoi or a Nix flake. A dotfiles manager usually owns whole files, though, and agents write to their own config files all the time. This is what fleet does differently.

      

      

        

          
✕ A dotfiles manager

          
✓ fleet

        

        

          
Owns all of settings.json
Claude Code writes to that file itself, so when the manager owns the whole file, the next apply overwrites what the agent wrote.

          
Owns only the keys you list
Fleet sets the keys your config lists, like attribution, and leaves the rest of the file to the agent. Hand edits to its keys are a conflict, not a silent overwrite.
~/.claude/settings.json
  attribution.commit   fleet's
  permissions.allow    the agent's
  model                yours

        

        

          
An MCP server per agent, per file
Claude Code and opencode store MCP servers in different files and shapes, so you keep two copies in sync by hand.

          
One catalog entry, both agents
Define the server once in catalog/mcp.yaml. Fleet writes it in each agent's own format, and fleet doctor starts it to check it answers.

        

        

          
Waits for you on each machine
You run an update or a rebuild on every host and hope you didn't forget one.

          
Reaches them for you
fleet push applies on every host over ssh while you watch. Machines it can't reach catch up on their own 30-minute timer.

        

        

          
Skills are just files
An upstream skill changes what your agent does, and nothing shows you the change before it lands.

          
Skills are pinned and reviewed
Every source is pinned to a commit. --review shows what an update brings in, with new scripts and URLs flagged.

        

      

      

        
Keep chezmoi for your dotfiles.Fleet only owns agent config, so the two sit side by side as long as chezmoi does not manage ~/.claude.

        
All in on Nix?home-manager has Claude Code and opencode modules. Fleet works without Nix, keeps encrypted secrets per host and stops at conflicts.

        
Rules for many agents?rulesync generates config for more than 60 AI coding tools from one set of rule files. Fleet keeps the setup of Claude Code and opencode the same on every machine.

v2.2.0
12 Nov 2026
1 security3 added3 changed3 fixed

  
Security
  • fleet apply no longer puts a Claude MCP server's decrypted secrets on a command line. It used to add a server with claude mcp add-json, which takes the whole entry as an argument, and any user on the host could read that from the process list while it ran. Fleet now writes the entry into ~/.claude.json itself, holding the same ~/.claude.json.lock Claude takes around its own writes, so a running Claude session neither loses fleet's entry nor has its own save lost. Removing a server still uses claude mcp remove, which carries no secret.

  
Added
  • The landing page is served from rolflab.nl/fleet. deploy/Dockerfile builds it as a container that serves site/ under /fleet/. The old GitHub Pages address redirects there, keeping the section of the link.
  • track: releases in fleet.yaml makes fleet update follow releases instead of a branch. It moves the pin to the newest release, the highest vX.Y.Z tag (tags with a suffix such as v3.0.0-rc.1 are ignored), and prints tool: <old> -> v2.2.0 (a1b2c3d) with the changelog sections in between; --json adds release. On the newest release it says up to date (v2.1.0); a pin that is already past it stays where it is until the next release. A move to a new major version adds a line to read "You need to do" before you push. A repo with no release tag exits 2. Any other track is a branch, as before.
  • fleet status --json and status --all --json carry conflictList for each host: its first 5 conflicts as kind and path, in the order status --conflicts lists them, so a row can name what is wrong. conflicts is still the count. A host that cannot plan its conflicts has null for both, and a host on an older fleet has no conflictList. The Omarchy widget shows the first one on the host's row.

  
Changed
  • The README and the landing page show a new screenshot of the Omarchy widget, with a host's row naming its first conflict.
  • fleet new writes track: releases, so a new config takes finished versions and not every commit on main. To keep following a branch, change track in fleet.yaml.
  • The landing page's title is now "fleet · One config. Every machine.", the same line as its heading, in the browser tab and in link previews.

  
Fixed
  • fleet doctor in a shell with no user session, as after sudo -iu, no longer reports a running timer as a problem: systemd cannot be asked from there, so the timer is unknown, with the reason and that doctor over ssh or from a login shell can see it. It does not count as a problem or change the exit code. With a session, a timer that gives no answer is still a problem.
  • fleet context and the bridge's context screen say why a server has no size. A server that wants a login says it needs one, so doctor cannot list its tools, instead of telling you to run fleet doctor again. A server whose last doctor run failed names that result. --json items have a doctor field with what the last doctor run found.
  • On the landing page, the bridge's keys keep working after you click one of its tabs or key chips; before, they only worked while the terminal itself had focus. The feature cards with an example now span the row, text beside the example, so the short cards next to them no longer stretch into tall empty boxes.
