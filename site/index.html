Fleet keeps the setup of your coding agents the same everywhere. Instructions, skills, MCP servers, settings and encrypted secrets live in one private git repo, and every machine is made to match it.

How it works

Write it once. Every machine follows.

Your config is a git repo you own. fleet push publishes it and applies it on every host it can reach over ssh. Every machine also pulls and applies on its own every 30 minutes.

fleet-config private

  • ⚙config/settings
  • 🔒︎secrets/*.enc.yaml
  • ▤hosts/

fleet push

Watch it land.

On a terminal, fleet push shows each step as it happens: validate, publish, then one line per host with its stage, a bar for the step it is on, and its time. When it ends, the block turns into a summary that stays in your scrollback. Everything below was recorded from the real command.

fleet push 

      

      
Hosts run one at a time. The conflict on server stops it and tells you the fix; fleet never overwrites what it did not write.


      

        
Piped, or in CI

        
Without a terminal there is no block to redraw. You get one timestamped line when each host starts and when it has a result, plus anything a host says. NO_COLOR turns the color off and keeps the block; piping is how you get plain lines. The result on stdout and in --json is the same either way.

What it keeps in line

        
Everything your agents need. Nothing they shouldn't.

        
How it works shows what fleet manages. These parts keep it safe to run on every machine and get a machine's setup into your config.

      

      

        

          

            
!

            
Conflicts, never overwrites

            
If a machine holds something different from your config, fleet stops and tells you exactly what and how to fix it. Hand edits and tool-written changes are never silently replaced.

          

          
✕ ~/.claude/CLAUDE.md is a file, not a link
  fix move it aside, then run fleet apply

        

        

          

            
✓

            
Skill review

            
A skill is instructions your agent follows, so an update from someone else changes what it does. fleet skills update --review reads what a source would bring in before its pin moves: the commits, the skills you use that changed, and a flag for each new script, new URL or wider allowed-tools.

          

          

        

        

          

            
▤

            
Startup context

            
Before your first prompt, each agent has already loaded your instructions, the descriptions of your skills and the tool definitions of your MCP servers. fleet context draws that as bars, in estimated tokens, with every host on one scale, so you see which machine and which server weighs the most. It only reads files and starts no server.

          

          

        

        

          

            
⇣

            
Capture

            
Set something up on one machine first, with claude mcp add or a skill folder. Then fleet capture turns the servers and skills that machine has and your config does not into config. It asks about each one, writes the catalog and the host files, and commits. A token in a server's env or headers moves into sops on the way, and no value is ever printed. It reads only the machine it runs on. Capture has the details.

          

          
$ fleet capture
[h]ost / [a]ll hosts / [i]gnore / [s]kip / [q]uit: h
ISSUES_API_KEY becomes the secret ISSUES_API_KEY.

Compare

        
Why not just dotfiles?

        
You could keep agent config in chezmoi or a Nix flake. A dotfiles manager usually owns whole files, though, and agents write to their own config files all the time. This is what fleet does differently.

      

      

        

          
✕ A dotfiles manager

          
✓ fleet

        

        

          
Owns all of settings.json
Claude Code writes to that file itself, so when the manager owns the whole file, the next apply overwrites what the agent wrote.

          
Owns only the keys you list
Fleet sets the keys your config lists, like attribution, and leaves the rest of the file to the agent. Hand edits to its keys are a conflict, not a silent overwrite.
~/.claude/settings.json
  attribution.commit   fleet's
  permissions.allow    the agent's
  model                yours

        

        

          
An MCP server per agent, per file
Each agent stores MCP servers in its own file and shape, so you keep a copy per agent in sync by hand.

          
One catalog entry, every agent
Define the server once in catalog/mcp.yaml. Fleet writes it in each agent's own format, and fleet doctor starts it to check it answers.

        

        

          
Waits for you on each machine
You run an update or a rebuild on every host and hope you didn't forget one.

          
Reaches them for you
fleet push applies on every host over ssh while you watch. Machines it can't reach catch up on their own 30-minute timer.

        

        

          
Skills are just files
An upstream skill changes what your agent does, and nothing shows you the change before it lands.

          
Skills are pinned and reviewed
Every source is pinned to a commit. --review shows what an update brings in, with new scripts and URLs flagged.

        

      

      

        
Keep chezmoi for your dotfiles.Fleet only owns agent config, so the two sit side by side as long as chezmoi does not manage ~/.claude.

        
All in on Nix?home-manager has Claude Code and opencode modules. Fleet works without Nix, keeps encrypted secrets per host and stops at conflicts.

        
Rules for many agents?rulesync generates config for more than 60 AI coding tools from one set of rule files. Fleet keeps the setup of your coding agents the same on every machine.

fleet card

        
Show your fleet.

        
fleet card writes fleet-card.svg, an image of your fleet to share in a post, a README or a GitHub discussion: the counts of machines, agents, skills and MCP servers, each machine with its agents and OS, and a year of changes. v2.6.0
18 Nov 2026
6 added1 changed1 fixed2 you need to do

  
Added
  • Antigravity CLI (agy) is a supported agent, the first one beyond Claude Code and opencode. A machine that has it gets its settings (settings.antigravity in a host file, written to ~/.gemini/antigravity-cli/settings.json; the keys the CLI writes itself, such as trustedWorkspaces, model and permissions, are refused), its MCP servers in ~/.gemini/config/mcp_config.json, skills linked into ~/.gemini/config/skills and instructions linked to ~/.gemini/GEMINI.md. Fleet touches only ~/.gemini/antigravity-cli, ~/.gemini/config and ~/.gemini/GEMINI.md, so Gemini CLI, which shares ~/.gemini, and other tools that link skills into the same directory are left alone. Antigravity CLI does not support SSE servers: an sse server whose only names antigravity is an error, and one without only goes to the other agents, is left out of its file, and a machine that has agy says so in one warning line in fleet diff and fleet apply. docs/mcp-logins.md says how Antigravity CLI signs in to MCP servers.
  • docs/adding-an-agent.md and CONTRIBUTING.md say what it takes to add an agent: the adapter and its registry line, an official documentation link for every path, key and format, the conformance suite, a fake binary and the lists, and the bar an agent has to meet. The README, the landing page and fleet agent each have a Supported agents list, and the one in fleet agent comes from the registry.
  • A machine now gets only the agents installed on it. Fleet finds an agent by its program (claude, opencode, agy) on the usual paths, in mise's shims (~/.local/share/mise/shims, where Omarchy installs agy) and in the directory of the Node it runs under, where npm -g puts agent CLIs, which also covers the timer, whose PATH has no fnm. Config for an agent that is not installed is not applied, and what fleet applied for it earlier is left as it is, never removed; installing the agent sets it up at the next apply. Skills are linked while any agent that reads their directory is installed. When an agent that fleet applied config for earlier is gone, fleet says so on every apply, diff and status, and on the bridge's host card. It says nothing about an agent the machine never had, opencode included: fleet status on a machine without it no longer ends in (opencode not installed). The warning reads "opencode: not installed, its config is left as is. Install it, or pin agents:". Nothing changes for a machine that has every agent. See setting up machines.
  • agents: [claude, opencode] in a host file (or the defaults) names the agents a machine gets instead of detecting them. A host file's list replaces the defaults' list, an unknown id is an error, and a named agent is set up whether or not it is installed (Claude's MCP servers still wait for claude). fleet agent has a recipe for taking an agent's config off a machine: take it out of the config and push while the agent is still installed, then pin it out.
  • fleet status shows the agents a machine gets (agents: claude 2.1.4, opencode 1.4.2, with (opencode not installed) and (pinned) where they apply). status --json has agents, one {id, version, active, pinned} per agent the machine has installed, names in agents: or applied config for, and notInstalled, the ids of the agents that warning is about. tools keeps its claude and opencode keys (null when not found) and gains a key for any other agent only where the machine names it; a host on an older fleet that sends neither agents nor notInstalled is still read. A host card in the bridge lists only the agents its machine gets.
  • fleet ui: the Agents boxes of the MCP server form show the agents some machine has or names, and "Show all agents" reveals the rest. An agent that is not shown keeps its value, so hiding it never narrows a server's only.

  
Changed
  • fleet context --json (and context --all) lists only the agents a machine gets, so a machine without opencode has no opencode entry. fleet doctor likewise checks only their servers.

  
Fixed
  • fleet doctor --all and the bridge no longer fail on a host whose fleet knows an agent this one does not: that agent's servers are left out of the doctor grid, and the bridge's context view skips the agent, instead of rejecting the host's whole answer.

  
You need to do
  • Nothing, if your config is unchanged and every agent you use is installed on each host: the plan and fleet context --json are the same as before, and fleet status --json only gains fields. What changes with 2.6.0 is this. A host now gets only the agents installed on it, and config for an agent it lacks is not applied there and is never removed (agents: in a host file names the agents instead of detecting them). fleet status and status --json gain agents and notInstalled and no longer mention an agent a host has never had (a host without opencode no longer shows opencode in the text); tools keeps its keys. fleet context --json lists only the agents of the host. A host with Antigravity CLI installed gets its config at the next apply; one without it is not changed and does not hear of it. To give Antigravity CLI the shared instructions, add { source: config/AGENTS.md, target: ~/.gemini/GEMINI.md } to files.
  • Every host has to be on 2.6.0 before a host file uses agents: or settings.antigravity, because an older fleet rejects a key it does not know. Move your pin with fleet update, read what it prints, and fleet push.
