How it works

Write it once. Every machine follows.

Your config is a git repo you own. fleet push publishes it and applies it on every host it can reach over ssh. Every machine also pulls and applies on its own every 30 minutes.

Watch it land.

On a terminal, fleet push shows each step as it happens: validate, publish, then one line per host with its stage, a bar for the step it is on, and its time. When it ends, the block turns into a summary that stays in your scrollback. Everything below was recorded from the real command.

fleet push 

      

      
Hosts run one at a time. The conflict on server stops it and tells you the fix; fleet never overwrites what it did not write.


      

        
Piped, or in CI

        
Without a terminal there is no block to redraw. You get one timestamped line when each host starts and when it has a result, plus anything a host says. NO_COLOR turns the color off and keeps the block; piping is how you get plain lines. The result on stdout and in --json is the same either way.

What it keeps in line

        
Everything your agents need. Nothing they shouldn't.

        
How it works shows what fleet manages. These are the parts that keep it safe to run on every machine.

      

      

        

          

            
!

            
Conflicts, never overwrites

            
If a machine holds something different from your config, fleet stops and tells you exactly what and how to fix it. Hand edits and tool-written changes are never silently replaced.

          

          
✕ ~/.claude/CLAUDE.md is a file, not a link
  fix move it aside, then run fleet apply

        

        

          

            
✓

            
Skill review

            
A skill is instructions your agent follows, so an update from someone else changes what it does. fleet skills update --review reads what a source would bring in before its pin moves: the commits, the skills you use that changed, and a flag for each new script, new URL or wider allowed-tools.

          

          

        

        

          

            
▤

            
Startup context

            
Before your first prompt, each agent has already loaded your instructions, the descriptions of your skills and the tool definitions of your MCP servers. fleet context draws that as bars, in estimated tokens, with every host on one scale, so you see which machine and which server weighs the most. It only reads files and starts no server.

Compare

        
Why not just dotfiles?

        
You could keep agent config in chezmoi or a Nix flake. A dotfiles manager usually owns whole files, though, and agents write to their own config files all the time. This is what fleet does differently.

      

      

        

          
✕ A dotfiles manager

          
✓ fleet

        

        

          
Owns all of settings.json
Claude Code writes to that file itself, so when the manager owns the whole file, the next apply overwrites what the agent wrote.

          
Owns only the keys you list
Fleet sets the keys your config lists, like attribution, and leaves the rest of the file to the agent. Hand edits to its keys are a conflict, not a silent overwrite.
~/.claude/settings.json
  attribution.commit   fleet's
  permissions.allow    the agent's
  model                yours

        

        

          
An MCP server per agent, per file
Claude Code and opencode store MCP servers in different files and shapes, so you keep two copies in sync by hand.

          
One catalog entry, both agents
Define the server once in catalog/mcp.yaml. Fleet writes it in each agent's own format, and fleet doctor starts it to check it answers.

        

        

          
Waits for you on each machine
You run an update or a rebuild on every host and hope you didn't forget one.

          
Reaches them for you
fleet push applies on every host over ssh while you watch. Machines it can't reach catch up on their own 30-minute timer.

        

        

          
Skills are just files
An upstream skill changes what your agent does, and nothing shows you the change before it lands.

          
Skills are pinned and reviewed
Every source is pinned to a commit. --review shows what an update brings in, with new scripts and URLs flagged.

        

      

      

        
Keep chezmoi for your dotfiles.Fleet only owns agent config, so the two sit side by side as long as chezmoi does not manage ~/.claude.

        
All in on Nix?home-manager has Claude Code and opencode modules. Fleet works without Nix, keeps encrypted secrets per host and stops at conflicts.

        
Rules for many agents?rulesync generates config for more than 60 AI coding tools from one set of rule files. Fleet keeps the setup of Claude Code and opencode the same on every machine.

v2.3.0
14 Nov 2026
4 added4 changed

  
Added
  • The landing page has a section on why not just dotfiles, a release pill and a What's new section, and rolflab.nl/fleet/changelog/ lists every release with a filter for each kind of change. They are generated from this file: npm run site:changelog rewrites them, and a test fails when this file changes without it.
  • Every fleet push now writes a journal on the host that ran it: ~/.local/state/fleet/pushes/<time>-<pid>.jsonl, a header (time, commit pushed, which host or all, how it ended) and the push's events with their times. The last 20 are kept, the file is private to you (0600), it is never shared between hosts, and it never makes a push fail. In the bridge, h on the push screen lists the recorded pushes, enter replays one at its real speed, and the end of a push says how much faster or slower it was than the last push of the same scope, such as 1.4s faster than the last push. There is no command for it.
  • fleet push --host <name> publishes as usual, then applies only on that host: this one, or one with an ssh: destination. From the laptop, --host box does not apply here, so a conflict on this host does not stop it; --host with this host's own name is the same as publishing and then fleet apply. A host without an ssh: destination (it applies on its own timer) or an unknown name is refused with exit 2 before anything is published, and the unknown-name message lists the valid names. It takes the push lock. --host was already a fleet bridge flag and still is.
  • fleet push --json lists what changed on each host. Each entry in hosts gains created, updated and removed, copied from that host's apply --json (key entries are {file, path}, link entries carry a target; no values), and changes is still the count. A host that gave no document (timer, unreachable, error) has empty lists. The text summary shows the counts by kind and the time of each host's apply, such as server: ok · 2 links, 1 key (1.8s).

  
Changed
  • The landing page's feature cards are trimmed to conflicts, skill review and startup context, plus one strip for secrets, pinned skills, the MCP doctor and agent use.
  • The bridge's push screen shows time and what each host got. The pipeline row has the total elapsed time and each lane its own, and a host that is connecting over ssh says so from the start, with its time running. An activity feed lists every event with its time and host, and a host pane (↑ and ↓ pick the host) shows what was written there so far and how many writes remain, then after the push what it got, from the created, updated and removed lists of the end document. From 100 columns everything shows, below 100 the host pane goes, and below 80 the feed goes too. r on a lane after the push runs fleet push --host <name> for it, and f on a lane with a conflict opens the Conflicts screen on that host.
  • fleet push shows each host's progress live on a terminal: a block on stderr with validate, publish and apply, then one line per host with its stage, a bar for its step and its time, replaced when the push ends by a summary that stays in the scrollback (on a terminal the same lines are not printed again on stdout). Piped, or in CI, it prints one timestamped line when each host starts and when it has a result, plus the host's own text; stdout and --json are unchanged. Ctrl-C prints the summary so far and exits 130, and this corrects the 2.0.0 line that push "reports each machine as it finishes", which it did not.
  • Only one fleet push runs at a time. A second one, from a terminal or the bridge, stops at once with a push is already running (pid N) and exit 7 (locked), instead of racing the first. The lock is ~/.local/state/fleet/push.lock, held from validate until the last host is done and let go on every way out; one left by a process that is gone is taken over. It is separate from the apply lock, which still covers one host's files.
