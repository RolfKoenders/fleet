What is on the pageAPIWho can reach itPushingOn a server

fleet ui starts a small web server inside the fleet process, prints its URL and opens your browser on it. The page shows every host, edits the config and pushes with live progress. It is a way to do from a browser what the bridge does in a terminal. Like the bridge, it is for you, not for an agent: fleet agent does not list it, and it has no --json form.

fleet ui                  # a free port, opens the browser
fleet ui --port 8765      # a fixed port
fleet ui --no-open        # print the URL and do not open a browser

It stops on ctrl-c, or by itself after 10 minutes with no page open. A push or a host set-up that is running when you press ctrl-c is its own process and finishes without the page; the terminal says so and points at fleet status. For a host set-up it also says that nothing will remove the host file if init fails.

Reload, and when the server goes away

  • Reload is safe. The token is kept in sessionStorage, which belongs to that tab alone (it is never in the address or the history after the page loads, and no other tab sees it). So F5 keeps the page working. The To push list is kept there too and comes back after a reload: it holds only edits, and an edit never holds a plain secret value (a value goes to the server once, in its own request, and the edit is sops ciphertext). While a push or a host set-up runs, the browser asks before the tab is closed or reloaded.
  • A tab that joins mid-run catches up. The server tells every new page which jobs run (a push, fleet init of a host, a clone, a check, a secret being encrypted, every host being asked for the Fleet screen) and replays the last events of the running push or init, so a second tab or a reload shows the lanes and log so far, and labels the job correctly (a host set-up is not shown as a push). The header names every running job.
  • Not answering. If fleet ui stopped, was restarted, or this machine slept, the header says not answering and a banner says what to do: run fleet ui again and open the new URL in the same tab. Push, Add and Set value are off meanwhile, and the page keeps trying.
  • Token no longer valid. If the server answers but refuses the page's token, it was started again. The page stops retrying (a refused token never becomes valid), says so, and the To push list is restored when you open the new URL in the same tab. A new tab without the URL cannot do anything, as before.

What is on the page

A header with this host, its checkout and whether the live connection is up (it reconnects by itself if the server drops it), and a menu: Fleet, Matrix, Catalog, Hosts, Capture, Secrets, Card, Review & push and Status. The page opens on Fleet. The page is plain files under src/ui/static/ that fleet serves as they are: no build step, no framework and no dependency, and nothing is loaded from another origin, including its font (JetBrains Mono, bundled in src/ui/static/fonts/ with its licence, a copy of the landing page's).

Fleet

The first screen: every host in the config at once, and what each loads before the first prompt. It is the bridge's host cards and fleet context --all in a browser.

  • What was last seen comes first. The screen opens on what the bridge remembered of each host, marked seen 2 h ago, not live, and then asks every host: when the screen opens and again on Refresh, never on a timer. Each ask is an ssh call per host (the status and the startup context, the same read-only questions the bridge asks), so it runs as a job: the page stays usable while it runs, the header says asking every host, and each host's card changes as its answer arrives. A second page that asks while one is out waits for that one, so the hosts are asked once.
  • The memory is the bridge's own file, ~/.local/state/fleet/bridge-hosts.json, read and written by the page and the bridge alike, so each opens on what the other last saw. It holds each host's last good status and startup context cut to what the cards show, no secret, and it is written when a host answers. This host is read in place and is not remembered, as in the bridge.
  • A card for each host, this host first: ok, or conflicts naming the first one, or unreachable over ssh with when it was last seen (and what it said then, kept and marked), or timer for a host with no ssh destination, whose status cannot be asked. Under it, when it last applied, its timer, what is pending, its fleet checkout and its agents, with a word for one fleet has applied config for and cannot find. A card that shows memory instead of an answer has a dashed edge and says not live.
  • The fix of a conflict. A host that reports conflicts is asked for them in full, like the bridge's Conflicts screen does, and its card gets a Show the fix button that opens each conflict with what is wrong and the command that clears it. A host on an older pin says that its detail needs a newer pin. A host that did not answer has no detail to show.
  • Startup context for every host and agent, as bars on one scale: a full bar is the heaviest agent of any host, so hosts can be compared. A bar is split into instructions, skills and MCP servers, and under it is what each weighs. A server nobody has measured makes the total a lower bound: it is shown with a + (~4.2k+) and never as zero, and the MCP part says not measured. A host with no startup context says why (an older pin, no ssh destination, unreachable); one that is only remembered is marked not live.
  • Doctor is not on this screen. It starts the MCP servers with their real credentials, which asking the hosts must not do.

Matrix

Named like the bridge's Matrix screen and read the same way. One row per skill bundle and per MCP server, one column per host. A bundle row opens to show its skills, which are read-only. A cell says where the item comes from for that host:

CellMeaning
✓ defaultthe defaults give it
+ addedthe host's own file adds it
✕ excludedthe host (or the defaults) excludes it
· offnothing picks it

Clicking a cell makes the smallest edit to that host's file, as a change to push: an item the defaults give is taken away with exclude in the host's file (the defaults are not edited), an item the host added is taken out of its list, an exclude is taken back. Clicking the same cell again takes that edit back. Hovering a cell says what a click will do: give, take away or undo. A host's name is a button that shows its file in the pane beside the table, as it will be written, with comments, blank lines and list style kept; nothing is on disk yet. The + Add button in the header offers what the Catalog's does, plus a host. A server, skill source or bundle you add is a row of the Matrix at once, off for every host, held like any edit.

Search

The Matrix and the Catalog each start with a search field that filters their rows (or cards) by name as you type, without regard to case. A bundle also matches when one of its skills does (a source matches by the skills fleet has read from it too): on the Matrix its row says skill review when that is why it is shown, and its matching skills are highlighted when it is open.

  • / goes to the field, unless you are typing in another field or a dialog is open. Esc clears the field, and blurs it when it is already empty.
  • The filter is part of the page address, as a query of the screen (#/matrix?q=git), so a reload keeps it and the address can be copied. The token is handled as before. Opening another screen from the menu starts without a filter.
  • It only hides rows. To push and Review & push are never filtered. When the filter hides rows that have an edit on To push, the field says so (2 hidden with changes, with their names as its tooltip).
  • A filter that matches nothing says so and has a Clear the filter button.

Catalog

The MCP servers, skill sources and skill bundles your hosts can pick from. The + Add button in the header offers an MCP server, a skill source or a skill bundle, and so does the dashed tile at the end of each section. Adding one gives it to no host: pick it in the Matrix. An addition is a change to push, so it shows in Review & push like a pick does, and one that is on To push has a Remove from push button (which takes back the picks of it too).

Each choice opens a dialog (a native modal <dialog>): focus goes to its first field and stays inside (Tab wraps), the page behind does not scroll, and Esc or Cancel closes it and leaves nothing behind, no edit to push and no form state, so it opens blank next time. Enter in a field does what the main button does. Beside the form the dialog shows the YAML that will be written as a diff against the file (catalog/mcp.yaml or catalog/skills.yaml), asked from the server as you type, so it is the server's own splice and not a copy of its rules. Every rule below is the server's and is also checked by the page before the click, in the same words. While the input is not valid yet, the pane lists what is still missing instead. Add to push puts the edit on To push and closes the dialog. On a phone the dialog fills the screen and the diff stacks under the form.

  • An MCP server. A name, whether it runs on the machine (a command) or at a URL (http or sse), the environment (or, for a URL, headers) as a plain value or secret:NAME, and which agents get it (the boxes are the agents this machine has, another machine last reported through the bridge, or a host file names; "Show all agents" reveals the rest, and an agent that is not shown keeps its value, so hiding it never narrows the server to fewer agents). A secret can never be in the command (the loader's rule, with its message), and a command such as npx pkg or uvx pkg with no version gets a warning and can still be held. A URL holds no credentials (user:pw@) and no space: put them in headers as secret:NAME. A row with a value and no name is told to give it a name. A name is at most 64 characters, and names compare without regard to case (WEB1 next to web1 is refused, because a source is a directory of that name and some tools lower-case a server's). An addition already on To push says already added to To push.
  • Check it starts. Runs doctor's probe on the one server you are adding, on this machine, and shows its tools and their size in tokens. It asks first, naming the command: it runs with the real credentials fleet can read for this host and may download packages. A secret that has no value on this host is left out and named, so the server starts without it. Nothing is written.
  • A skill source. A name, a repo (a URL, an scp-style address or a path on this machine), a path and an optional branch. Look at the repo clones it shallowly into a temp directory, lists its skills and reads its head commit. A pinned source (the default) is written with that commit, track for the branch and review: true; a followed one with its branch. A repo has no credentials in it (user:pw@, or a token as the user of an https URL): use a git credential helper or an ssh key; the page and the server refuse it, and an error that echoes a URL shows it without its userinfo. The repo, branch and path are checked before Look at the repo, which stays off while one is wrong, and a clone that fails is shown as an error under the button. The temp clone is deleted when you close the dialog, when a newer one replaces it and when the server stops.
  • A bundle. A name and its skills, picked from the sources fleet has cloned and from a source you hold, or typed in.

Edit

Every card on the Catalog (MCP server, skill source, skill bundle) and on Hosts has an Edit button next to its YAML toggle. The Matrix has none. Edit opens the Add dialog of that kind with the current values filled in, titled Edit ..., with the same live YAML diff and checks. The name is read-only, because renaming would leave host files pointing at nothing. Save to push puts the edit on To push, where it shows in Review & push like any other, and Remove from push on the card undoes it. Esc and Cancel close the dialog and leave nothing behind.

  • What each dialog changes. An MCP server: everything the Add dialog has except the name (command or URL, kind, environment or headers, which agents). A skill bundle: its skills. A skill source: path, branch, whether it is pinned or followed, and review; the repo is read-only, because a changed repo would break the clones machines already have (a source's clone is kept under its name and its origin is never reset), so another repo is another source. A host: its ssh destination only; its bundles and servers stay on the Matrix, and admin, age, vars, settings and files stay hand-written.
  • Only what changed is written. An edit holds each field it changes with what the file held before (from) and what it should hold (to). Every other key and comment in the file and in the entry stays byte for byte; a changed value keeps the comment at the end of its line, a cleared field is removed with its line, and a new key is placed where the entry writes its keys. A list of skills changes by line: a skill that goes loses its line, a new one follows the one before it, and the rest keep their comments. The result is read again and must be exactly the old document with the changes made.
  • Secrets. A secret:NAME row shows the name, and can be switched between a secret and a plain value. A value is never shown or sent: setting one stays on the Secrets page, and a name that has no value on a host shows the same tag as in Add.
  • A field that is as the file has it is not checked again. A rule the file may have been written without (a {{ vars.NAME }} in a URL, a variable name Add would not offer, an unpinned command) does not block an edit of another field. A field that changes is checked as in Add.
  • A skill source. Changing only the path or review leaves the pin where it is and needs no clone. Changing the branch, or switching between pinned and followed, looks at the repo first, as Add does (a shallow clone in a temp directory, deleted when the dialog closes): a pinned source moves its commit to the head of the new branch, and the dialog says so (The pin moves to 1a2b3c4, the head of dev) and lists the skills found.
  • An unpushed addition is changed in place. Editing an item whose addition is still on To push changes that addition. An edit of an item is also changed in place: the dialog starts from the file with the held edit on top, and when it is put back to what the file says, saving takes the edit off To push.
  • Stale edits. If the file says something else for a field at write time, the edit is dropped with a clear message ('servers.docs.command' is not what this edit was made from: it has changed in the file), Review & push lists it and holds the push until you forget it, and the newer value is never overwritten.
  • Entries fleet cannot change safely. Anchors, aliases, tags, flow maps for an entry, a flow list over several lines, block text (|, >), items not on lines of their own and Windows line endings are refused by the engine rather than guessed at. The button stays: Edit opens a dialog that shows the item's lines read-only, the reason, and the file to edit by hand. An anchor or alias anywhere in a file makes every entry in that file read-only, because the engine reads the whole file.

Remove

Every card on the Catalog (MCP server, skill source, skill bundle) and on Hosts has a Remove button next to Edit and YAML. The Matrix has none. It opens a dialog (a native modal <dialog>, like Add and Edit) that says what will change and shows the YAML diff of every file touched; nothing is staged or run until its button is pressed. Esc and Cancel close it and leave nothing behind.

  • An MCP server or a bundle is taken out of its catalog entry and out of every reference to it: mcp.include and mcp.exclude for a server, bundles and exclude for a bundle, in hosts/_defaults.yaml and in each host file. The dialog lists every host (and the defaults) it touches. The removal goes on To push as one held edit, so the config still loads for every host after it, and Remove from push on the item's card (drawn dimmed, tagged removal to push, while the removal is held) undoes it as a unit.
  • A skill source is taken out of the catalog, and its skills out of every bundle that lists them. The dialog says what each bundle loses (core loses 3 skills). A bundle left with no skills is kept, as [] (the config allows it), and is flagged in the dialog and on its card (no skills). Which skills a source provides is what the page knows of it: its clone on this machine, or what it saw when the source was added; a skill that another source also provides stays. When the page cannot tell (no clone here), the dialog says so, and bundles keep their skills. The clone of the source on each machine is left alone.
  • An item whose addition is still on To push is not staged for removal: removing it drops the addition, and every edit or pick of it that was held. Nothing is written.
  • The edits that name the item (a host's pick of it, an Edit of it) are dropped when the removal is held, because they would be stale after it; the dialog lists them.
  • What goes with the entry. The entry's own lines go, with the comments inside it and the comment lines right above it (the lines the YAML view shows for the item), and the blank line that set it apart. Every other comment and blank line, in the catalog and in the host files, stays byte for byte. A section left with no entry is written as {}, which the loader reads as empty, and an Add writes into it again.
  • Stale. If the item is already gone from the file at write time, or the file has a shape the engine refuses, the removal is dropped with a clear message ('docs' is not in catalog/mcp.yaml), Review & push lists it and holds the push until you forget it, and nothing is written.
  • A host is removed at once after you confirm, like adding one, not through To push. The server takes the push lock, deletes hosts/<name>.yaml and secrets/<name>.enc.yaml (if there), runs the real fleet secrets rekey as a child process (so .sops.yaml and the shared secrets file stop naming its key), then commits (Remove host <name>) and pushes the config repo. Its output is streamed into the page as it comes. When rekey or the commit fails, every file is put back and nothing is committed; when only the push fails, the commit stays and the page says to push it. The edits on To push for that host (its picks, its ssh edit, and a secret set for shared or for it, which the rekey makes stale) are dropped, and the dialog lists them. It refuses, like adding a host, while a push runs and while the config repo has changes the page did not make.
  • What the host dialog says. The machine keeps its files, and its timer will report errors until fleet is turned off there. It lists the secret names the host could read (those in shared, when it has a key, and those in its own file; names only, never a value) and says to change them: rekeying changes who can read the files, not the secrets' values. When the removal has finished, the dialog's Rotate these now button closes it and opens the Secrets screen on just those names (#/secrets?names=A,B), each with its Set value or Replace value button, and a notice with a link that shows every secret again. The page does not rotate anything for you and keeps no list: it cannot revoke an old token either. The command line does the same removal with fleet host remove <name>, which also stops the machine's timer over ssh, and has fleet secrets rotate for the values. See Retiring a machine.
  • Refused: for the host the page runs on, and for the only admin host (admin: true). The button is disabled with the reason as its title, and the server refuses the same.

YAML

Every MCP server, skill source and skill bundle on the Catalog, and every host on Hosts, has a YAML button (a toggle: aria-pressed, reachable and operable by keyboard). On, the card opens to show how the item is written in the config repo: its own lines in catalog/mcp.yaml or catalog/skills.yaml, with the comments right above it, or for a host the whole of hosts/<name>.yaml, under the file's path and in the same code style as the diffs. It is read-only and shows only what is literally in the file, so a secret is secret:NAME and never a value. When the item has an edit on To push (an addition, or a host file changed by a pick in the Matrix), the panel shows the diff of its lines against the repo instead, tagged to push: +N -M. Show all YAML in the header opens or closes every card of the screen at once. A screen reads the files again whenever it is opened.

Hosts

One card per host: how it is reached, and what it gets. + Add host, in the header and as the tile after the cards, opens a dialog that sets up a new machine from the page. Like the Catalog's, it is modal, takes focus, closes on Esc or Cancel with nothing written, and shows the host file that will be written (hosts/<name>.yaml, a new file) as a diff while you type, or what is still missing. Esc and Cancel are off while fleet init runs, because the run goes on without the page; after it ends, a failure keeps the form to try again and a success is closed with Done.

  • A name (the loader's rule for a host name), an ssh destination and where it starts from: the defaults only, or a copy of another host. ssh is required, because fleet init refuses a host without it; for a machine fleet cannot reach over ssh the form links setting up machines. A destination that starts with -, or has a space or another symbol, is refused, and so is one with no host after the @ (bob@) or with a port (bob@mini:22): set Port for the host in ~/.ssh/config instead. A name is at most 64 characters, shared is reserved (it is the secrets file every host reads), and a name that differs from a host only in case is refused, because on some disks it is the same file; the file is created only when nothing is there, so a failed init never removes a file it did not make.
  • A copy takes bundles, exclude, mcp, settings and vars of the other host, with the comments inside them, and not its ssh, age or files.
  • This is not a change to push. After you confirm (the page names the machine and what will run there), the server takes the push lock, writes hosts/<name>.yaml with the edit engine and runs the real fleet init <name> as a child process, so it commits and pushes itself (the host file, .sops.yaml and the re-encrypted secrets), exactly as from the CLI. Its output is streamed into the page as it comes: one line when each step starts and one when it ends, under a running clock (the page sets FLEET_INIT_PROGRESS=1 for the child; run from a terminal, fleet init prints its report at the end as always, and --json is unchanged).
  • It refuses while there are changes to push (the page asks you to push or discard them first, so init's commit does not sweep them in), while a push runs, while the config repo has changes the page did not make, and for a host that already exists.
  • When init fails before it committed anything, the host file is deleted and the files init rewrote are restored, so the repo is as it was. When init had already committed and pushed (for example the timer step failed on the host), the host file stays, because that commit is published; the page says so, and fleet init <name> finishes the rest when run again.
  • Removing a host is on its card: see Remove.

Capture

What this machine has that is not from config: MCP servers an agent was told about (claude mcp add) and skill folders copied in. It is fleet capture in a browser, for the machine the page runs on and no other. See Capture for what each choice does.

  • A card for each item, with where it was found and what it is: not in the catalog, matching the catalog (this host does not pick it), matching the config (take it over), or one fleet cannot capture, with why. The menu shows how many there are.
  • Choices. An item that is not in the catalog (or only matches it) is added for this host or for every host: the choice is worked out by the server into the same edits as Add (a catalog entry, a pick, a bundle, a source) and goes on To push, where Review & push shows each file's YAML diff. An item that already equals the config has a Take over button, which changes nothing in the config. Ignore on this host adds the item to unmanaged in the host file, as an edit to push like any other. Nothing is removed from the machine.
  • MCP servers. When the agents have the same server in different forms, the card shows each and you pick one. Each env variable and header is listed by name, with a secret box: it is on for names like *_TOKEN, *_KEY, *SECRET*, *PASSWORD* and Authorization, and you set it for any other. A secret has a name you can change. The value is read by the server from the agent's file, encrypted into the host's secrets file (or shared, for every host) with sops, and is never sent to the page: the page sees names only. A command that is not pinned to a version gets the same warning Add gives.
  • Skills. A skill in a git repo with a remote makes that repo a pinned source with review: true (or only a bundle, when it already is one); you name the bundle. A loose folder is listed with a message to put it in a repo first.
  • After the push this machine is taken over for what was captured, so the apply that follows finds nothing to change. If you reload the page before pushing, the choices and what is still to be taken over are kept for the tab.
  • Same name, other definition. An item with the name of a catalog entry and another definition is not listed; it is a conflict, and a line says how many there are.

Secrets

A table of every secret name against every host, by name only. A cell is set (the host's own secrets file has the name, or shared has it and the host can read shared), missing (a server the host picks, or its settings, use the name and neither file has it) or not used. A value to push shows as set with to push, and the tab counts the missing cells. Set value (Replace value when it is set everywhere it is needed) opens a password field:

  • A value of more than 8192 characters, or of only spaces, is refused with the limit named; the field never cuts what is typed. Typing a value here is allowed. It is sent to the server once, over the page's own connection, and is never logged, echoed, kept or sent back. The field is not named (a password manager does not offer to save it), asks for no autofill, and is emptied before the request goes; the page holds no copy of it in its state, storage or address.
  • The value is encrypted at once: the server copies the host's secrets file into a private temp directory (mode 0700), runs sops set --value-stdin there (the value goes on sops' stdin, never in argv or the environment) and reads the new file back. The directory is removed whatever happens, and the repo is not touched.
  • The result is a change to push that carries the encrypted file, shown in Review & push by its names with a short mark of each ciphertext. It is checked as strictly as a pick: the path must be a secrets file of shared or of a host with an age recipient, the text must hold nothing but ciphertext, it must be encrypted for exactly the recipients .sops.yaml names for that file, and it may add or replace only the names it says (no delete, no rename). It is written over the file it was made from only: when that file changed on disk since, the edit is dropped as stale and nothing is overwritten, and you set the value again.
  • It goes to the hosts that pick a server using the secret and do not have it yet, unticked others can be added, and shared is a choice of its own. A host with no age key cannot be chosen.
  • A failure is one of a few fixed sentences. What sops said is never passed on, because it can quote what it was given.
  • This sets and replaces. It does not delete or rename a secret: use fleet secrets for that.

Card

An image of your fleet to share: in a post, a GitHub discussion, or a README. It is an image because terminal text loses its colours the moment it leaves the terminal. The same card comes from fleet card, which writes fleet-card.svg (1200 x 630, the social preview size) in the current folder; the page shows what that command would write.

  • Two styles, switched at the top of the screen (fleet card --style machines|map, machines is the default). *Machines* has the four counts large (machines, agents, skills, MCP servers), a row per machine with its agents as badges and its OS, and a bottom line: N changes in the last year · N pushes since March 2026. *Map* puts the config in the middle and each machine as a card around it, with its agents, its OS and when it last applied (linux · 4m ago), and skills and MCP servers on the left of the bottom line, changes and pushes on the right. Above 6 machines the map shows 6 and a +N more card; machines shows 6 rows and +N more.
  • The activity grid. *Machines* shows a GitHub-style grid of the config repo's commits per day, five shades of green, but only when the repo had at least 20 commits in the last 12 months. Below that it is left out and only the bottom line stays, because an empty grid looks like a dead setup. The map has no grid.
  • What is counted. A change is a commit to the config repo, read from its git log. Pushes are the ones in this host's push journal, which keeps only the last 20, so a full journal reads 20+ pushes. The month is the one of the config repo's first commit. Skills and MCP servers are the ones some host gets, each counted once, and agents are counted once across hosts.
  • Privacy. Hosts are host 1, host 2 and so on, in name order, unless Show hostnames is on (--names in the CLI). The names of MCP servers, skills, skill sources and secrets are never on the card, with or without it, and neither is the startup context.
  • Nothing asks a host. Agents, OS and the last apply of each host are what the bridge last saw of it (the answers it keeps in ~/.local/state/fleet/bridge-hosts.json), and this host is read live, so the card works offline and without ssh. A host the bridge never saw is drawn without agents and OS, and the page says how many (never which, unless names are on): run fleet bridge once to read them.
  • Save PNG draws the card on a canvas at twice its size (2400 x 1260) and downloads it. The server draws the SVG, with the same code as the CLI, and the page only turns it into a PNG. Copy image puts that PNG on the clipboard; a browser that refuses (it needs a secure page and its permission, which 127.0.0.1 counts as) gets a plain message and Save PNG is the way round. Save SVG downloads the file fleet card writes. Post to Show and tell opens a new discussion in the Show and tell category of the project with a short title and text filled in (counts only, no hostname), in a new tab: you attach the image yourself.
  • Fonts. The SVG file names JetBrains Mono and then the monospace faces every system has (Fira Code, SF Mono, Menlo, Consolas, DejaVu Sans Mono), and Geist for the big counts, falling back to the same monospace. It embeds no font and fetches nothing, so it reads anywhere. The picture on this page and the PNG carry the bundled JetBrains Mono inside them, so they look as designed whatever is installed.
  • The README badge. fleet card --badge writes fleet-badge.svg, a small badge (fleet · 3 machines · 3 agents) in the same colours, for a config repo's README: !fleet. It holds no hostname.

Before it writes the file, fleet card prints what is on it, so you see what you are about to publish:

$ fleet card
  ● fleet   3 machines · 3 agents · 38 skills · 9 MCP servers

  host 1  claude opencode   linux

Review & push

  • The real diff of every file the changes to push change.
  • A check per host: whether its config loads with the edits (the same load fleet push starts with, and a host that would fail shows its problems), and its pick changes worked out from the config, such as + skills notes, deploy; − server docs.
  • This host only: the full plan, from fleet diff run on the edited config. It is worked out in memory and writes nothing. Other hosts are not planned, because that needs ssh; they get the pick summary instead.
  • A commit message, suggested from the edits and yours to change.

Write and push writes the files, commits them with the message, runs the real fleet push and shows each host's lane as it goes. Discard all drops the changes to push; until you push, nothing has touched the disk.

The page holds the edits as operations (add or remove of a bundle or server for a host, and addServer, addSource and addBundle for the catalog). The server rebuilds each from the fields it may have and checks an entry with the loader's own code, so the page can add nothing the loader would refuse. Every preview replays them, through the edit engine in src/edit/, on the files as they are on disk at that moment. An edit that no longer applies (the file changed under it) is listed as dropped with its reason, and nothing is written while any is.

Changes the page did not make. When the config repo has uncommitted changes of its own (git status --porcelain), the page lists them and refuses to write or push until you commit or discard them outside the page. The server checks again right before writing, so a change made after the page last looked is still caught. The server also refuses, before writing anything, while a push is running (a push is already running (pid N)), when an edit is stale, and when the edited config would not load for a host.

Who can reach it

The page can change your config and push, so nothing but you may reach it.

  • It listens on 127.0.0.1 only. There is no option to listen elsewhere.
  • The URL is http://127.0.0.1:<port>/#t=<token>: a random port and a random token. The page reads the token from the part after # (which a browser never sends to the server), keeps it in memory (and in sessionStorage of that tab, so a reload works) and sends it as a header on every call. There is no cookie. Opening the URL without the token shows a page that cannot do anything.
  • A request whose Host is not 127.0.0.1:<port> is refused, so a web page on another site cannot reach the server by pointing its own name at your machine (DNS rebinding). A write whose Origin is not the page itself is refused too.
  • The server sends no CORS header, so no other page can read an answer. Its pages may show images from the page itself and from blob: (the card, drawn into a canvas), and nothing from another origin.
  • The one call that cannot carry a header is the stream of live updates (a browser's EventSource cannot), so that call takes the token in its query instead. Nothing logs a URL.
  • A secret's value is never sent to the browser. Nothing the page sends is logged, and the one route that takes a value (/api/secrets/set) answers with the encrypted file and fixed messages only.

Pushing

A push from the page (and the one after Write and push) runs the real fleet push, so it takes the same push lock as a push from a terminal or the bridge. While another push is running, the page shows a push is already running (pid N) and starts nothing.

On a server

With SSH_CONNECTION set, fleet does not try to open a browser. The URL is printed, and you reach it from your own machine through a tunnel:

ssh -L 8765:127.0.0.1:8765 <the host>     # on your machine
fleet ui --port 8765 --no-open            # on the host

Then open the printed URL (with the same port) on your machine.
